# First real system-level live Flick GPU A/B: two successful timed rollback trials

**Date:** 2026-10-21, NixOS Lenovo Miix 2 10 tablet, normal DRM+seatd/TTY1 system service. Unlike all prior source/VM testing, this report describes **actual temporary activation and restarts of the hardware compositor**, authorized by the tablet owner. This is not a permanent NixOS activation.

## Timed systemd activation and recovery

Both trials used tools/flick-supervised-live-trial.sh in a root-only /run/vlenovo-flick-gpu directory, invoked with sudo -n through authorized SSH. The script checked active SSH/seatd/NetworkManager/Flick, the unchanged boot generation, GRUB generation 55 kernel/initrd, exact ELF and NixOS runtime wrapper SHA-256, then armed an independent 145-second root/systemd timer BEFORE modifying the Flick service. An explicitly marked, transient /run/systemd/system/flick.service.d/90-vlenovo-gpu-trial.conf override switched only the ExecStart of the existing service to its pinned user-owned launcher. The original /etc/systemd/system/flick.service, bootloader and Nix generation were never edited.

- Qt EGL-only candidate: activated 04:13:39 UTC (Flick PID 15353, qmlscene PID 15388); registry exposed wl_drm v2 and zwp_linux_dmabuf_v1 v5, QML had zero llvmpipe threads and four renderD128 file descriptors. Smithay logged both successful wl_drm renderer binding and DMA-BUF feedback registration. No flick.service journal warnings were observed.
- First rollback: timer ran at approximately 04:16:06 UTC, timer service Result=success, restored the original Nix store Flick ExecStart (PID 15986), removed all drop-ins; original QML again had four llvmpipe threads.
- Combined EGL+QML skip candidate: activated 04:16:47 UTC (Flick PID 16156, qmlscene PID 16191), same wl_drm and zwp_linux_dmabuf Wayland globals, zero llvmpipe threads and four DRM render node handles in QML. No flick.service journal warnings in observed interval. Flick RSS about 137.8 MiB and QML RSS about 127.5 MiB at end of measurement.
- Second rollback: timer ran at approximately 04:19:14 UTC, timer service Result=success, restored original Flick ExecStart (PID 16882), removed drop-ins; original QML had four llvmpipe threads again and essential services were active. Boot/current Nix generations remained identical.

## Measured CPU

Raw /proc jiffy trace output is preserved in mvp/native/benchmarks/2026-10-21-flick-live-qt-egl-56s.csv and mvp/native/benchmarks/2026-10-21-flick-live-qt-egl-qml-87s.csv. Both samples used the same script as earlier 30-minute original baselines, on the same physical tablet. Reproducible results in mvp/native/benchmarks/2026-10-21-flick-real-live-ab-cpu.md generated by tools/compare-flick-live-gpu-ab.py.

The original two 1804-second baselines averaged Flick 91.8%/92.4%, QML 33.7%/33.6% of one core, with four llvmpipe threads. EGL-only short run measured Flick 92.7%, QML 2.2% over 56 seconds. Combined short run measured Flick 15.5%, QML 13.4% over 87 seconds; both client cases had zero llvmpipe workers. The two-process combined CPU changed by approximately **-77.1%** relative to the mean original CPU baseline, for the observed short, unsupervised workload. QML CPU was **higher in the combined run** than the EGL-only run, a remaining question for frame-update cadence and graphics correctness. Do not claim equivalent animation/visual activity from process liveness alone.

GPU transport availability was checked from the live client's actual Wayland registry on both trials; read-only logs are saved at mvp/native/benchmarks/2026-10-21-flick-live-qt-egl-wayland.txt and ...flick-live-qt-egl-qml-wayland.txt.

## Limitations

Neither trial had a remotely verifiable screenshot, touch gesture, physical display observation or unlocking interaction. These results establish normal service startup, Wayland GPU transport discovery, QML DRM render node use and measured CPU for short idle lock-screen windows; they do not prove flawless visual frame composition, no flickering, complete unlock flow, hotplug/rotation or long-term memory stability. The live-optimized compositor was rolled back automatically in both cases, not made permanent.

Physical GRUB generation 55/56 were verified as recovery choices. If hardware seat release or kernel GPU hangs prevent systemd from executing rollback, GRUB is an external recovery path but still needs physical access. Longer soak and repeated transitions are recommended before permanent promotion.
